# ШКВОРЕНЬ — зафиксированные решения (до кодирования)

Документ для `docs/decisions.md` в репозитории `~/Documents/shkvoren`. Собран из обсуждения
в Cowork-сессии (дизайн трёх экранов) — закрывает блок «5» аудита Qwen-спеков. Отменяет те
места product-spec / data-model, где предполагалась розница или B2B-тарификация — их в
продукте больше нет.

## 0. Продукт

Розницы нет. Один сценарий: **опт-ликвидация склада запчастей ГАЗ/УАЗ по себестоимости**.
Один ценовой уровень, один тип покупателя — оптовик/СТО/механик, который сразу набирает
партию. Всё в product-spec.md про `customers.kind`, скидки по типу клиента, отдельный B2B-тир —
вычеркнуть.

## 1. Мастер-источник данных

**Google-таблица — единственный источник данных.** Отдельной копии `parts` в Supabase не
заводим. Next.js читает/пишет в таблицу напрямую через Sheets API сервисным аккаунтом
(только с сервера, никогда из браузера), с кэшем на чтение 3–5 минут + кнопка «Обновить
сейчас» в админке.

Причина: один оператор, 278 позиций — задача синхронизации двух хранилищ (мастер/реплика,
владение полями) создаёт больше риска, чем экономит. Supabase, если понадобится вообще, —
только под лист «Заказы» (см. п.2), потому что там нужна атомарная запись, а не то, что
человек правит руками.

Если позже упрётесь в лимиты Sheets API (частые запросы с витрины) — тогда возвращаемся к
гибриду из аудита (Sheets = qty/цены, Supabase = карточки/фото/применимость), не раньше.

## 2. Что такое «заказ» и когда он создаётся

В момент клика «Отправить в WhatsApp» строка сразу дописывается в отдельный лист «Заказы»
той же таблицы: номер заказа, позиции, количество, сумма, **телефон покупателя**, статус
`новый`, timestamp. Потом — редирект в WhatsApp. Так заказ зафиксирован, даже если покупатель
не отправит сообщение.

**Телефон покупателя обязателен к запросу** на обоих экранах, где есть кнопка WhatsApp
(опт-витрина и экран заказа) — без него в логе заказа нет контакта для связи. В дизайне поле
уже есть и попадает в текст сообщения.

## 3. Тип документа

**Не фискальный документ.** Простой бланк-заказ под брендом «ШКВОРЕНЬ»: название, адрес
(рынок «Салем»), телефон продавца, позиции, итог, место для подписи. Без ИП/БИН, банковских
реквизитов, НДС — это разряд «квитанция/ордер», не счёт-фактура и не накладная в юридическом
смысле.

## 4. Номер заказа

Формат `ШКВ-0001`, инкремент = следующая свободная строка листа «Заказы».

## 5. Защита закупочной цены

При архитектуре «сервер читает Sheets, клиенту отдаёт только цену продажи» проблема снимается
структурно: закупочная цена просто никогда не сериализуется в ответ витрины. Явно
перечислить в контракте API, какие поля публичные (цена продажи, остаток, применимость), и
проверить это тестом (запрос к публичному эндпоинту не должен возвращать `cost_price`/
`закупочная`).

## 6. Вход в админку

Один пароль в переменной окружения + cookie-сессия. Supabase Auth и роли не нужны — оператор
один.

## 7. Марки

Только ГАЗ и УАЗ. Другие марки, если встретятся при импорте реальной таблицы (аудит находил
единичные ВАЗ/ЗИЛ/КамАЗ/МАЗ) — не showstopper, но в MVP не показываем; вопрос закрыт, не
переоткрывать без новых данных.

## 8. Остаток: число или флаг

Показываем точное число (опту нужно решение по объёму, не факт наличия/отсутствия). Явно
зафиксировать: пока нет кассы/POS, остаток после сделки корректируется в таблице вручную —
автоматического списания при подтверждении заказа в MVP нет.

## 9. Идентификатор позиции

Не генерировать SKU по бренду/каталогу. Добавить в саму Google-таблицу скрытую колонку `ID`
(сквозная нумерация 1..278) — она и есть первичный ключ везде (заказы, импорт, будущий
Supabase, если появится).

## 10. Применимость (fitment)

Хранить исходную строку как есть (`fitment_raw`), не парсить автоматически (в данных не менее
16 вариантов написания одного и того же). Нормализация — вручную, по мере необходимости.

## 11. Отображение каталожного номера

Дефисы/форматирование — только там, где формат уверенно распознан (длина и структура
совпадают с известной схемой ГАЗ/УАЗ). Для мусорных/аномально длинных значений — показывать
как есть, никогда не выдумывать разбивку. Если номера нет вообще — показывать явно «номер не
указан», не оставлять пустое место.

## 12. Текст WhatsApp-сообщения (зафиксирован, протестирован)

Без позиций:
```
Здравствуйте! Интересует распродажа склада ГАЗ/УАЗ по себестоимости.
Мой телефон: <телефон>
```

С позициями:
```
Здравствуйте! Хочу заказать по распродаже склада:
<номер> — <название>, <кол-во> шт x <цена> = <сумма>
...
Итого: <сумма>
Мой телефон: <телефон>
```

Строка с телефоном добавляется только если поле заполнено.

## 13. Номер WhatsApp получателя

`+7 777 250 84 20` — в переменную окружения (`NEXT_PUBLIC_WHATSAPP_NUMBER` или серверную,
в зависимости от того, собирается ли ссылка на клиенте), не хардкодить в компонентах.

## 14. B2B-цены отдельным уровнем

Снято за ненадобностью — весь сайт один ценовой уровень (опт/себестоимость).

## 15. Фото

В MVP без фото — подтверждено: в реальной таблице фото нет ни у одной позиции. Экраны в
дизайне свёрстаны без фото (плотный список, акцент на номере/цене/остатке), это не временная
заглушка, а осознанный вид MVP.

## 16. Сбор рыночных цен — цель и способ

**Цель зафиксирована первым сообщением этого чата:** рыночные цены нужны не для показа
покупателю на витрине, а **оператору в админке** — чтобы свериться и скорректировать
собственные закупочные/реализационные цены (уже отражено в дизайне `Admin-Gsheets.dc.html`:
колонка «Рынок» + % отклонения + кнопка-заглушка «Найти цену»). Показывать рыночную цену
на публичной витрине — отдельное решение, сейчас не принято и не нужно для цели.

Разведка (вечер 20.09) показала: живой автообход 4 сайтов (kaspi.kz, Kaspi JSON,
4uaz.ru, detaliuaz.ru, ozon.kz) `curl`-ом не работает — Kaspi отдаёт HTML без цены
(дорисовывается скриптом), Kaspi JSON-эндпоинт угадан неверно (405), у 4uaz.ru/detaliuaz.ru
угадан неверно путь поиска (404), Ozon отдаёт антибот-редирект (307). Отдельная проблема
данных: у 91 позиции из 278 нет артикула — сопоставлять с чужим каталогом по одному
названию ненадёжно (наименования вроде «Тормозной диск» массово не уникальны).

**Решение: не строить батч-краулер по всем 278 позициям.** Вместо него —
**поштучный поиск по запросу оператора**, ровно под уже спроектированную кнопку
«Найти цену» в строке таблицы:

- Клик по кнопке в конкретной строке → сервер запускает поиск (веб-поиск/поисковая выдача,
  не скрейпинг конкретных 4 сайтов по фиксированному URL-шаблону) по артикулу (если есть)
  или по названию+модели — и возвращает 1–3 кандидата с ценой и ссылкой на источник.
- Оператор сам подтверждает совпадение (маленький список, а не молчаливая запись) —
  это то же ручное подтверждение, что уже принято в п.1/п.8 для остальных данных таблицы.
  Только после подтверждения цена пишется в колонку «Рынок».
- Для позиций без артикула — обязательно ручное подтверждение совпадения, автоматическое
  сопоставление по имени не делать никогда (риск ложного соответствия).
- Полного покрытия по всем 278 не требуется сразу — начать с ходовых 20–30 позиций
  (наибольшая выручка/оборот по данным таблицы), остальное — по мере надобности оператору.

Причина отказа от батч-скрейпинга: Kaspi/Ozon защищены антиботом (обход через headless-
браузер возможен технически, но хрупкий, требует поддержки при любом изменении разметки,
и рискован с точки зрения ToS этих площадок для регулярного фонового обхода) — а
для цели «раз в час свериться по одной позиции, которую в данный момент правит оператор»
это избыточная сложность. Если объём вырастет и поштучный режим станет узким местом —
тогда пересматривать в сторону планового обхода конкретных страниц товара (не категорий/
поиска) с Playwright, отдельным решением.

## 17. Мгновенное уведомление о заказе

`wa.me`-ссылка (п.2, п.12) — это не автоматическая отправка: WhatsApp по дизайну (и по
условиям использования) не даёт сайту отправить сообщение за покупателя без его собственного
нажатия «отправить» в приложении — это ограничение WhatsApp, а не наше. Убрать этот шаг
для покупателя можно только через WhatsApp Business Platform (Cloud API от Meta) — а это
отдельная верификация бизнеса, привязка номера к Business API и, для первого сообщения в
переписке, одобренный шаблон — заметно тяжелее текущего MVP, поэтому отложено, не встроено.

**Что делаем сейчас:** покупательский `wa.me`-переход остаётся как есть (он же даёт
покупателю его собственную копию заказа в его WhatsApp). Отдельно, **в тот же момент**,
когда сервер дописывает строку в лист «Заказы» (п.2), он же отправляет уведомление
о новом заказе в Telegram — через Telegram Bot API (`sendMessage` на chat_id владельца/
рабочего чата). Это не требует одобрения, бесплатно, работает сразу и не зависит от
действий покупателя — именно то, что нужно для цели «продавец узнаёт о заказе мгновенно».
Текст уведомления — тот же состав, что в шаблоне WhatsApp (п.12) плюс ссылка на строку
в таблице/номер заказа.

Итого: WhatsApp остаётся каналом связи с покупателем (ручной, как и было), Telegram —
канал мгновенного оповещения продавца (автоматический, новый). Если позже понадобится,
чтобы и сообщение покупателю уходило без его клика — это переход на WhatsApp Business
API, отдельная задача с отдельной верификацией, не блокирует текущий MVP.

## Экраны (дизайн-референс)

Артефакт: https://claude.ai/artifact/DjpwQP7n9UiigmYbXsyyKY — три интерактивных экрана на
дизайн-системе «ШКВОРЕНЬ». Сам файл экрана (`.dc.html`) — формат редактора дизайна, не код
для переноса; Next.js/React-компоненты пишутся заново по мотивам, а не копированием разметки.
Для передачи в Claude Code/Qwen удобнее всего:

1. Открыть артефакт → включить Play на каждом артборде → сделать скриншоты (десктоп-ширина).
2. Положить скриншоты в `docs/design/` рядом с этим файлом.
3. Ссылаться на них из задач как визуальный контракт экрана.

Экраны:

- **Опт-витрина** (`Opt-Vitrina.dc.html`, 1280×900) — поиск, фильтр по марке, переключатель
  «только в наличии», плотный список позиций со степпером количества, живой пересчёт суммы,
  поле телефона, кнопки «Образец накладной» и «Отправить в WhatsApp» (текст собирается из
  реально выбранных позиций).
- **Заказ / бланк** (`Nakladnaya.dc.html`, A4, печать через браузер) — летерхед ШКВОРЕНЬ,
  список позиций с возможностью поправить количество перед отправкой, поле телефона
  покупателя, кнопки «Печать» (`window.print()`) и «В WhatsApp». Заголовок «Заказ №
  ШКВ-000N» — номер в реальном приложении берётся из листа «Заказы» (п.4), не из количества
  позиций, как в макете-заглушке.
- **Админка** (`Admin-Gsheets.dc.html`, 1440×900) — таблица с поиском, статус синхронизации с
  Google-таблицей, колонка «Рынок» с местом под будущего AI-агента цен (пока часть строк
  показывает пример отклонения, остальные — пусто), индикаторы «нет номера» / «нет в
  наличии».
