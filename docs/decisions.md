# ШКВОРЕНЬ — зафиксированные решения (до кодирования)

Документ для `docs/decisions.md` в репозитории `~/Documents/shkvoren`. Собран из обсуждения
в Cowork-сессии (дизайн трёх экранов) — закрывает блок «5» аудита Qwen-спеков. Отменяет те
места product-spec / data-model, где предполагалась розница или B2B-тарификация — их в
продукте больше нет.

## 0. Продукт

Розницы нет. Один сценарий: **опт-ликвидация склада запчастей ГАЗ/УАЗ по себестоимости**.
Один ценовой уровень, один тип покупателя — оптовик/СТО/механик, который сразу набирает
партию. Всё в product-spec.md про `customers.kind`, скидки по типу клиента, отдельный B2B-тир —
вычеркнуть.

## 1. Мастер-источник данных

**Google-таблица — единственный источник данных.** Отдельной копии `parts` в Supabase не
заводим. Next.js читает/пишет в таблицу напрямую через Sheets API сервисным аккаунтом
(только с сервера, никогда из браузера), с кэшем на чтение 3–5 минут + кнопка «Обновить
сейчас» в админке.

Причина: один оператор, 278 позиций — задача синхронизации двух хранилищ (мастер/реплика,
владение полями) создаёт больше риска, чем экономит. Supabase, если понадобится вообще, —
только под лист «Заказы» (см. п.2), потому что там нужна атомарная запись, а не то, что
человек правит руками.

Если позже упрётесь в лимиты Sheets API (частые запросы с витрины) — тогда возвращаемся к
гибриду из аудита (Sheets = qty/цены, Supabase = карточки/фото/применимость), не раньше.

## 2. Что такое «заказ» и когда он создаётся

В момент клика «Отправить в WhatsApp» строка сразу дописывается в отдельный лист «Заказы»
той же таблицы: номер заказа, позиции, количество, сумма, **телефон покупателя**, статус
`новый`, timestamp. Потом — редирект в WhatsApp. Так заказ зафиксирован, даже если покупатель
не отправит сообщение.

**Телефон покупателя обязателен к запросу** на обоих экранах, где есть кнопка WhatsApp
(опт-витрина и экран заказа) — без него в логе заказа нет контакта для связи. В дизайне поле
уже есть и попадает в текст сообщения.

## 3. Тип документа

**Не фискальный документ.** Простой бланк-заказ под брендом «ШКВОРЕНЬ»: название, адрес
(рынок «Салем»), телефон продавца, позиции, итог, место для подписи. Без ИП/БИН, банковских
реквизитов, НДС — это разряд «квитанция/ордер», не счёт-фактура и не накладная в юридическом
смысле.

## 4. Номер заказа

Формат `ШКВ-0001`, инкремент = следующая свободная строка листа «Заказы».

## 5. Защита закупочной цены

При архитектуре «сервер читает Sheets, клиенту отдаёт только цену продажи» проблема снимается
структурно: закупочная цена просто никогда не сериализуется в ответ витрины. Явно
перечислить в контракте API, какие поля публичные (цена продажи, остаток, применимость), и
проверить это тестом (запрос к публичному эндпоинту не должен возвращать `cost_price`/
`закупочная`).

## 6. Вход в админку

Один пароль в переменной окружения + cookie-сессия. Supabase Auth и роли не нужны — оператор
один.

## 7. Марки

Только ГАЗ и УАЗ. Другие марки, если встретятся при импорте реальной таблицы (аудит находил
единичные ВАЗ/ЗИЛ/КамАЗ/МАЗ) — не showstopper, но в MVP не показываем; вопрос закрыт, не
переоткрывать без новых данных.

## 8. Остаток: число или флаг

Показываем точное число (опту нужно решение по объёму, не факт наличия/отсутствия). Явно
зафиксировать: пока нет кассы/POS, остаток после сделки корректируется в таблице вручную —
автоматического списания при подтверждении заказа в MVP нет.

## 9. Идентификатор позиции

Не генерировать SKU по бренду/каталогу. Добавить в саму Google-таблицу скрытую колонку `ID`
(сквозная нумерация 1..278) — она и есть первичный ключ везде (заказы, импорт, будущий
Supabase, если появится).

## 10. Применимость (fitment)

Хранить исходную строку как есть (`fitment_raw`), не парсить автоматически (в данных не менее
16 вариантов написания одного и того же). Нормализация — вручную, по мере необходимости.

## 11. Отображение каталожного номера

Дефисы/форматирование — только там, где формат уверенно распознан (длина и структура
совпадают с известной схемой ГАЗ/УАЗ). Для мусорных/аномально длинных значений — показывать
как есть, никогда не выдумывать разбивку. Если номера нет вообще — показывать явно «номер не
указан», не оставлять пустое место.

## 12. Текст WhatsApp-сообщения (зафиксирован, протестирован)

Без позиций:
```
Здравствуйте! Интересует распродажа склада ГАЗ/УАЗ по себестоимости.
Мой телефон: <телефон>
```

С позициями:
```
Здравствуйте! Хочу заказать по распродаже склада:
<номер> — <название>, <кол-во> шт x <цена> = <сумма>
...
Итого: <сумма>
Мой телефон: <телефон>
```

Строка с телефоном добавляется только если поле заполнено.

## 13. Номер WhatsApp получателя

`+7 777 250 84 20` — в переменную окружения (`NEXT_PUBLIC_WHATSAPP_NUMBER` или серверную,
в зависимости от того, собирается ли ссылка на клиенте), не хардкодить в компонентах.

## 14. B2B-цены отдельным уровнем

Снято за ненадобностью — весь сайт один ценовой уровень (опт/себестоимость).

## 15. Фото

В MVP без фото — подтверждено: в реальной таблице фото нет ни у одной позиции. Экраны в
дизайне свёрстаны без фото (плотный список, акцент на номере/цене/остатке), это не временная
заглушка, а осознанный вид MVP.

## 16. Сбор рыночных цен — цель и способ

**Цель зафиксирована первым сообщением этого чата:** рыночные цены нужны не для показа
покупателю на витрине, а **оператору в админке** — чтобы свериться и скорректировать
собственные закупочные/реализационные цены (уже отражено в дизайне `Admin-Gsheets.dc.html`:
колонка «Рынок» + % отклонения + кнопка-заглушка «Найти цену»). Показывать рыночную цену
на публичной витрине — отдельное решение, сейчас не принято и не нужно для цели.

Разведка (вечер 20.09) показала: живой автообход 4 сайтов (kaspi.kz, Kaspi JSON,
4uaz.ru, detaliuaz.ru, ozon.kz) `curl`-ом не работает — Kaspi отдаёт HTML без цены
(дорисовывается скриптом), Kaspi JSON-эндпоинт угадан неверно (405), у 4uaz.ru/detaliuaz.ru
угадан неверно путь поиска (404), Ozon отдаёт антибот-редирект (307). Отдельная проблема
данных: у 91 позиции из 278 нет артикула — сопоставлять с чужим каталогом по одному
названию ненадёжно (наименования вроде «Тормозной диск» массово не уникальны).

**Решение: не строить батч-краулер по всем 278 позициям.** Вместо него —
**поштучный поиск по запросу оператора**, ровно под уже спроектированную кнопку
«Найти цену» в строке таблицы:

- Клик по кнопке в конкретной строке → сервер запускает поиск (веб-поиск/поисковая выдача,
  не скрейпинг конкретных 4 сайтов по фиксированному URL-шаблону) по артикулу (если есть)
  или по названию+модели — и возвращает 1–3 кандидата с ценой и ссылкой на источник.
- Оператор сам подтверждает совпадение (маленький список, а не молчаливая запись) —
  это то же ручное подтверждение, что уже принято в п.1/п.8 для остальных данных таблицы.
  Только после подтверждения цена пишется в колонку «Рынок».
- Для позиций без артикула — обязательно ручное подтверждение совпадения, автоматическое
  сопоставление по имени не делать никогда (риск ложного соответствия).
- Полного покрытия по всем 278 не требуется сразу — начать с ходовых 20–30 позиций
  (наибольшая выручка/оборот по данным таблицы), остальное — по мере надобности оператору.

Причина отказа от батч-скрейпинга: Kaspi/Ozon защищены антиботом (обход через headless-
браузер возможен технически, но хрупкий, требует поддержки при любом изменении разметки,
и рискован с точки зрения ToS этих площадок для регулярного фонового обхода) — а
для цели «раз в час свериться по одной позиции, которую в данный момент правит оператор»
это избыточная сложность. Если объём вырастет и поштучный режим станет узким местом —
тогда пересматривать в сторону планового обхода конкретных страниц товара (не категорий/
поиска) с Playwright, отдельным решением.

### 16.1. Разведка списка сайтов от 21.09 — что реально годится в источники

Kaspi и Ozon по запросу убраны из списка источников. Проверены 8 сайтов из присланного
списка (обычным HTTP-запросом, без headless-браузера — так же, как будет работать
серверный поиск по клику «Найти цену»):

| Сайт | Технически | Валюта/тип цены |
|---|---|---|
| `detaliuaz.ru` | ✅ стабильно — WordPress/WooCommerce, цена и артикул прямо в HTML товарной страницы (проверено: `1 764 ₽`, артикул `3163-10-3504010-00`) | ₽, розница |
| `uaz.store` | ✅ стабильно — цена и код товара прямо в HTML (`16784 руб`, `Код 00018`), поиск на `/search` | ₽, розница |
| `spectuninguaz.ru` | ✅ стабильно технически (CS-Cart, цена+код в HTML) | ₽, розница, явно позиционирован как обычный ритейл без опта |
| `4uaz.ru` | ⚠️ нестабильно — категории открываются, но карточка товара даёт «too many redirects» при прямом заходе (похоже на защиту от ботов) | не удалось получить |
| `vta-gaz.ru` | ⚠️ нестабильно — Bitrix, часть страниц 404/redirect-loop при прямом заходе; упоминает работу с юрлицами и НДС, но отдельной опт-цены не видно | не удалось получить |
| `metalpart.ru` | ⚠️ нестабильно — Bitrix, каталог даёт redirect-loop при прямом заходе | не удалось получить |
| `autogur73.ru` | ❌ отдаёт 403 на любой странице, включая найденные через поиск — заблокирован для автообхода | — |
| `chipdip.kz` | ❌ не тот профиль: это магазин электронных компонентов и паяльного оборудования, автозапчастей ГАЗ/УАЗ там нет — исключить из списка источников | тенге, но не по теме |

**Рекомендация — «что проще»:** `detaliuaz.ru` и `uaz.store` как основные источники (оба
стабильно отдают цену и артикул в обычном HTML-ответе, без браузера), `spectuninguaz.ru`
третьим. `4uaz.ru`/`vta-gaz.ru`/`metalpart.ru` не включать в MVP поштучного поиска — их
защита от ботов делает прямой запрос ненадёжным; если понадобятся, единственный рабочий
путь — headless-браузер (Playwright), отдельная задача. `autogur73.ru` и `chipdip.kz` —
исключить.

**Важная оговорка по сути данных, а не по технике:** все найденные цены — розничные и в
рублях, а не оптовые и не в тенге. Ни на одной из проверенных товарных страниц нет
отдельной «оптовой» цены — это нормально для B2B: поставщики обычно не публикуют оптовый
прайс в открытом каталоге, а дают его по запросу/после регистрации дилера. При разведке
нашёлся `uaz73.ru` («Группа компаний «Запчасти УАЗ оптом»», оптовые поставки по России и
ближнему зарубежью) — в открытом HTML цены нет, доступ к прайсу, похоже, только через
диалог с менеджером/VIN-подбор. Если у вас уже есть свои действующие поставщики (или их
прайс-листы в Excel/PDF, которые присылают по запросу) — это будет надёжнее и честнее
любого скрейпинга: цену из прайс-листа дилера можно грузить в колонку «Рынок» напрямую,
без поиска и без риска спутать деталь. Розничные цены с `detaliuaz.ru`/`uaz.store` в этом
случае остаются вторым, ориентировочным слоем («сколько это стоит конечному покупателю в
России») — обязательно показывать с пометкой валюты и без автоконвертации в тенге по
скрытому курсу (курс RUB/KZT колеблется, коэффициент должен быть виден оператору, не
зашит молча в код).

### 16.2. Доразведка 21.09 — найден источник получше: satu.kz

По просьбе поискать источники самостоятельно (не только по присланному списку) проверил
казахстанские маркетплейсы и оптовиков. Главная находка — **`satu.kz`**, и она меняет
приоритет источников:

- Цены отдаются прямо в HTML, **сразу в тенге** (`6 200 ₸`, `245 000 ₸`) — не нужна
  конвертация RUB→KZT и её скрытые риски курса, о которых предупреждал в п.16.1.
- Есть отдельные страницы под опт: `satu.kz/Uaz-zapchasti;wholesale.html`,
  `satu.kz/Zapchasti-gaz;wholesale.html` — то есть площадка явно размечает оптовые
  предложения, а не только розницу.
- На одной странице — предложения **нескольких разных продавцов одновременно**
  (Gricompani, «ИП УрАЛ запчасть», «ТОО Бриссоль», Avtolampa.kz и др.) с артикулами и
  названиями рядом с ценой. Это качественно другой уровень достоверности «рыночной
  цены», чем цена одного магазина — по сути уже готовая мини-выборка рынка на одну
  позицию.
- Оговорка: прямой эндпоинт поиска (`/search.html?search_term=...`) закрыт их
  `robots.txt` — уважаем это и не дёргаем его напрямую. Рабочий (разрешённый) путь —
  категорийные/opt-страницы вида `satu.kz/<Категория>;wholesale.html`, которые открылись
  без проблем. Для реализации это значит: серверный поиск по клику «Найти цену» на
  Satu.kz стоит делать через их официальный партнёрский/товарный API, если он у площадки
  есть (уточнить отдельно), либо — как временный вариант — просто давать оператору
  прямую ссылку на нужную категорию для ручной сверки, а не парсить обход по каждому SKU.

Также нашлись, но менее полезны технически: **`gricompani.kz`** (Алматы, тот же
продавец, что уже виден внутри Satu — оказался витриной на платформе Satu, отдельно
цены не отдаёт, только через JS) и **`askom.kz`** — на сайте есть прямая ссылка
«Скачать прайс-лист» (`price.xlsx`), это ровно тот случай из п.16.1 «прайс-лист от
поставщика напрямую» — надёжнее скрейпинга, но при попытке скачать программно файл по
найденной ссылке отдал 404 (возможно, ссылка требует захода с реальной страницы или
периодически меняется) — стоит скачать вручную через браузер и проверить, что в нём
реально есть, прежде чем встраивать в автоматику. **`uazshop.kz`** — цены закрыты
(«Цену уточняйте», без WhatsApp/звонка не узнать) — не подходит для автосверки.
`kolesa.kz` (доски объявлений, в т.ч. по УАЗ в Алматы) не проверен технически
(таймаут при проверке) — по типу данных это частные/разборочные объявления, а не
прайс дилера, приоритет ниже Satu.

**Обновлённая рекомендация по источникам:** `satu.kz` (opt-страницы категорий) —
первый приоритет, KZT и мультипродавец перевешивают розничные RUB-сайты из п.16.1;
`detaliuaz.ru`/`uaz.store` — вторым слоем как и раньше (ориентир в рублях, с явной
пометкой валюты); `askom.kz` прайс-лист — проверить вручную, если данные хорошие,
это лучший вариант из всех (структурированный файл от реального поставщика, а не
скрейпинг чужой веб-страницы).

## 17. Мгновенное уведомление о заказе

`wa.me`-ссылка (п.2, п.12) — это не автоматическая отправка: WhatsApp по дизайну (и по
условиям использования) не даёт сайту отправить сообщение за покупателя без его собственного
нажатия «отправить» в приложении — это ограничение WhatsApp, а не наше. Убрать этот шаг
для покупателя можно только через WhatsApp Business Platform (Cloud API от Meta) — а это
отдельная верификация бизнеса, привязка номера к Business API и, для первого сообщения в
переписке, одобренный шаблон — заметно тяжелее текущего MVP, поэтому отложено, не встроено.

**Что делаем сейчас:** покупательский `wa.me`-переход остаётся как есть (он же даёт
покупателю его собственную копию заказа в его WhatsApp). Отдельно, **в тот же момент**,
когда сервер дописывает строку в лист «Заказы» (п.2), он же отправляет уведомление
о новом заказе в Telegram — через Telegram Bot API (`sendMessage` на chat_id владельца/
рабочего чата). Это не требует одобрения, бесплатно, работает сразу и не зависит от
действий покупателя — именно то, что нужно для цели «продавец узнаёт о заказе мгновенно».
Текст уведомления — тот же состав, что в шаблоне WhatsApp (п.12) плюс ссылка на строку
в таблице/номер заказа.

Итого: WhatsApp остаётся каналом связи с покупателем (ручной, как и было), Telegram —
канал мгновенного оповещения продавца (автоматический, новый). Если позже понадобится,
чтобы и сообщение покупателю уходило без его клика — это переход на WhatsApp Business
API, отдельная задача с отдельной верификацией, не блокирует текущий MVP.

### 17.1. Telegram-получатель — готово, проверено

## 18. «Предложить свою цену»

Новая фича по запросу — покупатель может предложить свою цену, а не только соглашаться на
цену из таблицы. Решено (21.09): и на уровне отдельной позиции, и на уровне всего заказа
сразу, оба варианта опциональны — по умолчанию всё работает как раньше (обычная цена из
таблицы, без единого лишнего клика для тех, кто не хочет торговаться).

**Где именно:**

- **По позиции** — в строке рядом с суммой по строке добавляется скрытая по умолчанию
  ссылка/кнопка «Предложить свою цену», по клику разворачивается небольшое поле ввода
  «Ваша цена за шт». Если заполнено — именно эта цена участвует в подсчёте суммы по
  строке и в общем итоге вместо цены из таблицы. Пусто — ничего не меняется.
- **По всему заказу** — в order bar, рядом с полем телефона, ещё одно необязательное поле
  «Предложить свою сумму за весь заказ». Если заполнено — оно перекрывает собой любые
  построчные цены (в т.ч. предложенные) для итоговой суммы и текста сообщения: одна
  цифра на весь заказ, без разбивки по позициям — так и должно быть, если покупатель
  торгуется за партию целиком, а не за одну деталь.
- **Приоритет, если покупатель заполнил и то и другое:** сумма по заказу побеждает
  (проще для сценария «сколько заплачу в итоге», не нужно разбираться в комбинации из
  15 построчных цен). Построчные предложения в этом случае всё равно передаются в текст
  сообщения и в лист «Заказы» как есть — для истории и чтобы было видно, с чего
  покупатель отталкивался.

**Валидация:** только базовая — число, больше нуля, без верхней/нижней отсечки по
проценту от цены в таблице. Никакого автоматического запрета «нельзя ниже себестоимости»
не делаем: цена в таблице и так уже себестоимость (§0), значит предложение ниже неё —
осознанный сценарий («лишь бы ушло с остатков»), а не ошибка ввода. Решение — соглашаться
или нет — всегда ручное, за Дмитрием в переписке; сайт ничего не подтверждает и не
пересчитывает остаток сам.

**Как это доходит до Дмитрия:**

- Текст WhatsApp (дополняет шаблоны из п.12): если есть построчные предложения — рядом с
  такой строкой добавляется пометка `(предложено: <цена> ₸/шт)`; если заполнено поле
  «сумма за заказ» — оно заменяет собой «Итого» на `Итого (предложение покупателя):
  <сумма>`.
- Лист «Заказы» (п.2): к составу строки добавляются необязательные поля `offered_total`
  (число или пусто) и, если были построчные предложения, они входят в `items[]` вместе с
  обычной ценой — так видно и что было в прайсе, и что предложил покупатель.
- Telegram-уведомление (§17): если в заказе есть любое предложение цены — в начало
  сообщения добавляется пометка вроде `💬 Покупатель предложил цену` — чтобы Дмитрий не
  пролистал мимо и не подтвердил заказ по умолчанию как «по прайсу», не заметив, что
  сумма другая.

**Что не делаем:** авто-подтверждение/авто-обновление остатка или цены в таблице по
предложению покупателя, торг в несколько раундов на самом сайте (контрпредложение,
таймер и т.п.) — вся торговля дальше первого предложения уходит в переписку WhatsApp,
сайт передаёт только первый шаг.

### 18.1. Доводка по факту проверки на проде (23.09)

При живой проверке нашлось два расхождения:

1. **Карточка товара (`/product/:id`) не получила «Предложить свою цену».** Задача 11
   ставила это на «строку товара (каталог и/или корзина)» — карточка отдельной
   страницы товара в этот список не попала явно, хотя по смыслу должна: покупатель
   может зайти на конкретную позицию не через список, а напрямую (ссылка, поиск), и
   там сейчас нет способа предложить цену за эту позицию. Нужно добавить туда тот же
   паттерн (скрытая ссылка → инпут «Ваша цена за шт»), что уже работает в корзине —
   один и тот же компонент/логика, просто ещё одно место применения.

2. **Комментарий к заказу.** Добавить на чекауте (там же, где телефон и предложение
   суммы за заказ) небольшое необязательное текстовое поле «Комментарий к заказу»
   (не жёстко валидировать, разумный лимит длины — символов 200–300, чтобы не раздувать
   сообщение). Если заполнено:
   - добавляется строкой в текст WhatsApp (по той же схеме, что телефон/предложение —
     только если не пусто, `Комментарий: <текст>`);
   - пишется в отдельную колонку листа «Заказы» (следующая свободная после I/J);
   - попадает в текст Telegram-уведомления, поскольку оно строится из того же текста,
     что WhatsApp (§17) — отдельно ничего дублировать не нужно.
